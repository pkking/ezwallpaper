# ezwallpaper — Product and Release Roadmap

**Scope:** from the existing cross-platform wallpaper Core/CLI to reliable dual-monitor niri + Noctalia usage, then unified desktop, lockscreen, login and boot backgrounds. This roadmap specifies *release acceptance*, not a release calendar or a count of Pull Requests.

**Last reviewed:** 2026-11-14. Release status and proof can change: check the actual [GitHub Releases](https://github.com/pkking/ezwallpaper/releases), [Epic #60](https://github.com/pkking/ezwallpaper/issues/60) and [versioned goal-gate matrix](docs/agents/goal-gates.md). A merged PR or successful unit/CI test does not itself mean a real physical user scenario passed.

## Release stages

| --- | --- | --- | --- |
| **M1 — v0.3.0-alpha.1** | **Source-only integration preview.** Local assets and opt-in providers; headless Core and CLI; persistent two-output rotation; native Noctalia IPC; experimental niri *virtual* compositor proof | Matching Cargo versions, source-install and limitations documented, exact-head CI and source-package checks pass; GitHub tag points to CI-verified release commit, marked **prerelease** with no unverified binary assets. Physical/timer acceptance not required | **Preparation in [#314](https://github.com/pkking/ezwallpaper/issues/314) / [PR #315](https://github.com/pkking/ezwallpaper/pull/315); not claimed released here** |
| **M2 — v0.3.0-beta.1** | **Real desktop acceptance candidate.** Supported released niri + Noctalia; actual mixed-resolution dual-monitor hourly wallpaper changes | Operator-approved real 3840×2160 scale 1.5 + 1080×1920 portrait session with independent pixels and recovery; released niri compatibility; real user-systemd timer crosses adjacent UTC hours with different output content IDs; critical failures recorded and repaired | **BLOCKED_EVIDENCE** — G-01/G-02 have isolated virtual proof and operator tools, not physical/timer proof |
| **M3 — v0.3.0 stable** | **Supported, maintainable dual-monitor wallpaper release.** Clearly bounded Linux/niri/Noctalia compatibility and safe upgrade/rollback | All M2 gates stay green on supported release versions; controlled end-to-end extended run including real hourly timer, offline/restart/failed IPC/recovery, output disconnect/reconnect; documented installation, upgrades, uninstall/rollback and release package integrity; no unresolved release-blocking safety or data-loss defects | **NOT READY** — requires M2 evidence and release qualification |
| **M4 — v1.0.0** | **Complete Epic #60 desktop-integration goal**, in addition to M3 stable wallpaper basics | Same-epoch desktop+lockscreen+SDDM+Plymouth independently validated, including root-owned import and initramfs/next-boot semantics; optional dynamic video/poster integration and truthful weather/agent-status widgets; comprehensive asset lifecycle, limits and platform compatibility | **PLANNED / PARTIAL CONTRACTS** — cross-surface and dynamic user outcomes remain unverified |

These are release **quality gates**, not automatically scheduled deadlines. The maintainers can narrow or broaden scope only through a documented Issue/ADR and an updated acceptance matrix. **M3 is intentionally narrower than M4:** a usable wallpaper application does not need to promise hourly Plymouth/initramfs rebuilds or a full lockscreen widget suite.

For M3, keep a **small, explicit support matrix** for verified combinations of released niri, Noctalia, display scaling, GPU/driver and operating system. Do not claim broad macOS/Windows/other Wayland desktop pixel compatibility from compilation or offline tests. Fix any release-blocking crash, data loss, unsafe path/credential handling, silent wallpaper-owner conflict or unrecoverable state regression before publishing the stable tag.

## M4: complete desktop visual integration

- **G-03 — [#56](https://github.com/pkking/ezwallpaper/issues/56):** a single hour/epoch drives the desktop, lockscreen, SDDM and Plymouth image selections. Each surface requires independently tested real results. The greeter may cache images; changing a pathname is not evidence the live login screen refreshed. Plymouth images packaged inside initramfs apply according to the next-boot boundary; **do not promise hourly boot images or perform hourly initramfs rebuilds** without a separate safe architecture decision.
- **G-04 — [#58](https://github.com/pkking/ezwallpaper/issues/58):** video wallpaper/poster frame pipeline, Noctalia vs mpvpaper renderer ownership and actual lockscreen animations; date/weather and accurate executing-agent counts belong to their respective Noctalia/external provider services, not to the headless wallpaper Core. Never substitute OS process count for real Agent task count.
- **G-06 and lifecycle — [#52](https://github.com/pkking/ezwallpaper/issues/52), [#53](https://github.com/pkking/ezwallpaper/issues/53), [#57](https://github.com/pkking/ezwallpaper/issues/57):** sourcing, derivation, provenance, retention and explicit previewable garbage collection across sessions.
- **Release qualification:** evidence on all *advertised* platforms/surfaces; install/upgrade/rollback and failure recovery. Unsupported surfaces are labeled and must not silently downgrade advertised capabilities.

## Release decision rules

1. **Release proof before labels.** Use `IMPLEMENTED`, `VIRTUAL_VERIFIED`, `PHYSICAL_VERIFIED` and `BLOCKED_EVIDENCE` as defined in [goal-gates.md](docs/agents/goal-gates.md). A tool being merged, a sample CI fixture or green pull request does not authorize a higher proof level.
2. **Beta/no-go:** unresolved released-niri compatibility or missing real mixed-DPI physical and timer evidence blocks M2; do not relabel an experimental virtual success as Beta-ready.
3. **Stable/no-go:** missing M2 evidence, nonreproducible install/update/rollback, critical image/state loss or unrecoverable wallpaper conflicts block M3. Functional tests must match the *supported release version*, not only an experimental branch.
4. **v1/no-go:** incomplete user-visible cross-surface or promised dynamic integration blocks M4. If Plymouth per-hour update is infeasible, document a user-approved scope adjustment instead of falsely closing the Epic.
5. **Agent priority:** finish the highest unmet P0 user gate first; include `Epic`, `Goal`, `Before`, `After`, `Evidence plan` and `Remaining unassessed` in new PRs. After three merged implementation PRs for one gate, reassess the end-to-end proof rather than opening another marginal isolated test.
6. **No phantom releases.** A milestone is published only when GitHub shows its actual Tag/Release, exact commit, package result and prerelease/stable flags. Maintain a changelog and keep open Issues until their entire user acceptance scope passes.

## Where progress is tracked

The [Epic #60](https://github.com/pkking/ezwallpaper/issues/60) owns user objectives; [goal-gates.md](docs/agents/goal-gates.md) records detailed evidence by G-01..G-06; GitHub Issues specify testable deliverables; [AGENTS.md](AGENTS.md) and [workflow.md](docs/agents/workflow.md) enforce the PR/plan/CI workflow; [Releases](https://github.com/pkking/ezwallpaper/releases) are the authoritative version publication record. Roadmap milestones never auto-close Issues or create release tags.
